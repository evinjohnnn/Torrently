# Frontend and backend connections

Initial checkout: no frontend, network calls or backend existed. The following connection contract is grounded in the exact pinned source revisions in `upstream.lock.json`; application implementation is in `client/api.ts`, `shared/contracts.ts`, and `server/`.

| User action | Torrently adapter responsibility | Verified upstream operation |
|---|---|---|
| Sign in/out, profile | Local secure session cookie, CSRF, persistent user records | No upstream account credential sent to browser |
| Paste magnet / upload .torrent | Validate/bound body; resolve and persist real metadata | `POST /api/v1/resource` with raw body and `Content-Type: application/x-bittorrent` |
| Read torrent | Enforce user resource access | `GET /api/v1/resource/:resource_id` |
| List files | Page through full upstream result; validate safe paths and IDs | `GET /api/v1/resource/:resource_id/list?output=list&limit=1000&offset=N` |
| Direct playback/download | Mint user-bound media ticket; proxy bytes, cancellation and Range | `GET /api/v1/resource/:resource_id/export/:content_id`, `exports.download.url` |
| HLS remux | Rewrite every manifest child URI through authorized adapter | `exports.stream.url`, usually `~vod/.../index.m3u8` |
| CPU transcode fallback | Create session and retain upstream signed query server-side | Derived `~hls/session`, `POST` returns `{id,duration}` |
| Transcode seeking / cleanup | Explicit session API, not plain direct-file seeking | `POST ~hls/session/:id/seek?t=N`, `DELETE ~hls/session/:id` |
| Folder/torrent ZIP | Use directory/root item id, stream bytes without full buffering | Same export endpoint, `exports.download.url` routes through `~arch` |
| Torrent SRT subtitle | Convert on upstream, serve WebVTT through authorized proxy | SRT item's `exports.stream.url` routes through `~vtt` |
| Personal library/favorite/progress | Per-user database rows owned by Torrently | No shared upstream library used |
| Engine health | Authenticated readiness request; return configuration/outage honestly | `/api/v1` contract, no internal admin endpoint published |

## Shapes

`ResourceResponse`: `{id,name,magnet_uri,multi_file,file?,size,files_count}`. IDs are normalized infohash strings.

`ListResponse`: root `ListItem` plus `{items,items_count}`. `ListItem` includes `{id,name,path,type,size,media_format,mime_type,ext,index}`. IDs from the listing identify exports; index is also accepted for files. Directories are not media files. List mode is recursive/flattened; tree mode is optional. Preserve the full path so nested folders can be reconstructed without inventing hierarchy.

`ExportResponse`: `{source,exports}`. Each export can contain `{url,html_tag,meta}`. Names include `download`, `stream`, `torrent_client_stat`, `media_probe`, and `subtitles`; unavailable exports are absent. A video does not necessarily include subtitle tracks. A `.srt` item's own stream export is the VTT conversion route.

## Authentication and origin constraints

The external prefix is `/api/v1`. nginx deliberately does not expose `/rest-api/`, whose process has no authentication of its own. `/api/v1` requires `Authorization: Bearer <API credential>` generated by an authorized administrator from Webtor's profile. It mirrors rest-api paths with API-specific errors and scope checks. Non-form Content-Type is necessary so global CSRF middleware does not consume raw torrent/magnet bytes.

Export URLs have the configured DOMAIN and `/torrent-http-proxy/<infohash>/...` path prefix. Their query contains the engine signing key/token, distinct from the API Bearer credential. Keep both server-side. An adapter must validate the configured origin and that exact media path prefix before fetching; do not accept arbitrary client-supplied URLs or redirects. Browser-visible URLs must point back to the adapter's authorized media route. HLS manifests can use relative, absolute-path or absolute URIs, including URI attributes on key/map/media tags: resolve against the upstream playlist URL, validate, and rewrite all forms.
